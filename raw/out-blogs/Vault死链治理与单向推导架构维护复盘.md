# Vault 死链治理与单向推导架构维护复盘

> **时间**：2026-07-08  
> **主题**：知识库图谱死链深度诊断、分类治理与级联清理安全边界  
> **目的**：为未来的 AI Agent 及知识库维护者提供抽象化指导与防错警示

---

## 1. 死链的实质分类与“假性死链”鉴别

在对知识库执行 `vault_lint.py` 等静态图谱审计时，扫出的“死链（Broken Links）”在表象下往往具有完全不同的物理根因。维护者切忌在未分类的情况下进行粗暴的批量一刀切清理，应严格按照以下三个维度进行鉴别：

### ① 命名缩写与全称不匹配（Naming Mismatch — 需重定向）
* **表象**：正文中引用了 `[[概念_GRPO]]`、`[[概念_PPO]]`、`[[实体_Anthropic]]`，被识别为死链。
* **根因**：作者（或 Agent 在 Ingest 提炼时）凭直觉或行业简称书写了链接，而库中实际存在的是更为精确的全称或带限定词的页面（如 `概念_GRPO强化学习.md`、`概念_PPO近端策略优化.md`、`实体_Anthropic_Research系统.md`）。
* **治理原则**：**绝对保留，精准重定向**。通过同义词映射将简称统一规范为全称，或利用 Obsidian 的 Alias 语法 `[[真实文件名|显示简称]]` 进行修复。

### ② 多余路径前缀干扰（Redundant Path Prefix — 需规范化）
* **表象**：链接书写为 `[[concepts/概念_xxx]]` 或 `[[entities/实体_xxx]]`。
* **根因**：受到底层相对路径思维影响，在链接中硬编码了文件夹前缀。虽然 Obsidian 的 `alwaysUpdateLinks: true` 机制在大部分交互场景下能兼容解析，但在静态 Lint 审计、严格图谱计算或跨层级移动时，极易引发解析断裂。
* **治理原则**：**去前缀化**。全库统一遵循无文件夹前缀的 `[[概念_xxx]]` / `[[实体_xxx]]` 维基链接标准。

### ③ 正常待建节点（To-be-created Stubs — 需容忍与观察）
* **表象**：指向如 `[[概念_训练并行策略]]`、`[[概念_CLAUDE.md最佳实践]]` 等尚无对应物理 `.md` 文件的链接。
* **根因**：知识库构建遵循《AGENTS.md》的自顶向下提炼范式。在 Ingest 阶段，为了预留图谱挂载点，前瞻性地抛出了核心概念与实体链接。在它们独立成文前，在 Obsidian 中呈现为紫色待建状态。
* **治理原则**：**保持容忍，按需生长**。这是知识网络生长弹性与复利潜力的体现。高频引用（如被引 $\ge 3$ 次）的节点应作为优先补建清单；低频引用（1~2 次）允许其长期作为待建提示存在，**严禁为了追求“0 死链率”而将其抹除**。

## 2. 级联清理（Cascading Pruning）的安全边界与防损红线

当核心底座（如 `raw/` 原始文献或 `wiki/sources/` 结构化摘要）因重构、弃用或重复被批量移除时，最容易引发图谱大面积断裂。对此，必须恪守以下工程纪律：

### ① 上下文联动的半衰期清理
* 当某篇 `sources/xxx.md` 被清理时，不仅要同步移除 `wiki/index.md` 中的总索引条目，还必须按照《AGENTS.md》中确立的**自上而下四步级联清理 SOP**，全文扫描其他相关笔记（特别是 `sources/`、`concepts/` 中的“相关来源”或“对比参考”清单）。
* 若现存页面中对已删文章的交叉引用失去了存在价值，需及时将 `[[已删页面]]` 解耦——根据语境决定是退化为纯文本记录，还是彻底摘除该条目。

### ② 行内安全清理红线（No Blind Line-Dropping）
* **痛点警示**：在脚本化批量剔除已删 source 引用时，如果简单粗暴地执行“只要行内匹配到死链，就删除整行（Line Deletion）”，会产生灾难性的**连锁误伤**。
* **经典场景**：例如正文中存在一行 `相关来源：[[RAG综述_中科院2025]]、[[向量数据库原理与应用全解析]]、[[从BM25到Multi-Vector演进]]`。当前者被删需要清理时，若直接删除整行，会将后两个合法、极具价值的现存双链一并永久抹杀。
* **核心纪律**：未来的自动化维护工具必须实现**“行内安全感知（Inline Safety Sensing）”** 。如果一行中除了待删死链外，还包含其他合法有效的双链，**必须且只能精确移除该死链本身及其配套的顿号/逗号分隔符**，绝不能造成同代节点的连带损失。只有当一行中仅存死链、无任何其他知识负载时，方可整体销毁。

## 3. 架构维护的基本指导思想

1. **坚持单向数据推导管线**：永远对 `raw/ -> wiki/sources/ -> wiki/entities|concepts` 的唯一推导链保持敬畏。末端产物的合法性必须完全建立在一级摘要层的基础上，任何越级直连底座的行为在 Lint 中都应被标记并纠正。
2. **路径重构必伴随全库锚定审查**：当对物理文件夹结构进行升级（如将 `raw/` 拆分为 `articles/`、`playbooks/`、`insights/` 等子目录）时，重构不仅是操作系统的文件移动，更是一场图谱关系的重定向手术。必须确保全库 YAML `sources:` 字段及正文双链实现 100% 同步适配与路径对齐。
3. **把工具作为辅助，把规范作为准绳**：Lint 报告是发现问题的听诊器，而非盲目动刀的指示灯。每一次优化修剪，都必须综合考量图谱的语义完整性、系统防腐性与未来复利价值。
