## 高德地图AI应用开发岗一面，我跪了！！！

> 面完出来，我坐在工位园区台阶上发了十分钟呆。

上周面了高德地图的 AI 应用开发岗。面试官一看就是那种天天泡在工程里的人，不绕弯子，上来就是一连串问题怼过来，从 RAG 到 Agent 到记忆管理，基本把我这半年攒的那点家底翻了个底朝天。

面完的感受怎么说呢—— **知道自己哪儿不行，比知道自己哪儿行，要清晰得多** 。

趁热乎，把还记得的问题整理出来。有的答上来了，有的答得稀碎，有的现在回头看还能再抢救一下。希望能给准备类似岗位的朋友一点参考。

## 1\. RAG 单轮和多轮推理的核心差别在哪里？

这个问题其实是在问：对话系统里，带上下文和不带上下文，RAG 的玩法有什么不同？

**我当时回答** ：单轮 RAG 就是针对当前这一个问题去检索、生成。多轮的话，你得处理历史的指代、省略，比如用户上一句说“那个路口”，这一句说“它旁边呢”，“它”指什么你得拎清楚。工程上要做问题改写、会话状态管理，还要压缩历史信息，不然一堆无关对话会把检索结果带偏。

**现在补充一下标准答案** ：

单轮 RAG 的流程可以简单理解为：

```
用户问题 → 向量检索 → 召回相关文档 → LLM 生成答案
```

多轮 RAG 得加一层“上下文理解”：

```
历史对话 + 当前问题 → 问题改写/意图补全 → 检索 → 历史信息融合 → 生成
```

举个例子，用户问了三轮：

- “北京今天天气怎么样？” → 返回晴天 28°C
- “那明天呢？” → 要自动补全为“北京明天天气怎么样？”
- “适不适合去香山？” → 要补全为“北京明天天气适合去香山吗？”

每一轮都在依赖前一轮的信息，这就是多轮的核心难点。

**面试官追问** ：多轮里历史对话怎么压缩？我当时答了摘要和滑动窗口，他点点头没再追问。现在想想，应该把 **Map-Reduce 式摘要** 和 **关键信息抽取** 的区别讲清楚。

## 2\. 需求匹配代码的场景，单轮还是多轮更合适？

这个问题很实际，不是考概念，是考你什么时候用什么。

**我的回答** ：需求明确的话，比如“找一下用户登录接口的实现”，单轮检索就够了。但如果需求有歧义，比如“把支付逻辑优化一下”，你得先搜到相关代码，看了之后发现支付逻辑分散在三个模块里，然后继续追问“订单模块的支付回调呢”，这就是多轮。

**面试官总结了一句** ： **不取决于谁更高级，取决于任务有没有前后依赖。**

这句话我记下了。很多时候我们容易被“多轮听起来更牛”带着走，但工程上合适比复杂重要。

## 3\. RRF 融合多路检索结果的原理是什么？

这道题我答得还行，因为我上周刚看了 RRF 的论文。

**我的回答** ：RRF（Reciprocal Rank Fusion）不比较不同检索器打出来的原始分数，因为向量检索的分数和 BM25 的分数根本不在一个量纲上。它的做法是看每个文档在每路结果里的 **排名** ，然后打分：

![公式](https://mmbiz.qpic.cn/mmbiz_svg/Q3auHgzwzM6ziaAEQylbTyOyUbQzsLCOqOeibw49U0v1ghOPJnyGt4uZAPkjnzKjGkLRiayicFoV7VJSUoU5U9vmsWBKrG7hNdEnebnNyHwaddSsH7O9ht1Ozw/640?wx_fmt=svg&from=appmsg#imgIndex=1)

是个常数，通常取 60。把所有检索路线的分数加起来排序，就是最终结果。

**面试官追问** ：为什么不用归一化分数再平均？

我当时顿了一下，然后说：归一化本身就不稳定，不同检索器的分数分布差异太大了，RRF 不依赖分数绝对值，只依赖排序，更鲁棒。

他点头了。

**补充一点原理图** ：

```
关键词检索 (BM25)   →  排名 [doc3, doc1, doc5, ...]
向量检索 (Embedding) →  排名 [doc1, doc5, doc2, ...]
语义检索 (Cross-Encoder) → 排名 [doc5, doc3, doc1, ...]

各路排名输入 RRF：
  doc1: 1/(60+2) + 1/(60+1) + 1/(60+3) = 0.0161 + 0.0164 + 0.0159 = 0.0484
  doc5: 1/(60+3) + 1/(60+2) + 1/(60+1) = ...
  按总分重新排序 → 最终融合结果
```

这个方法的好处是 **简单、稳定、不需要训练** ，工业界很喜欢。

## 4\. RRF 中的 k 一般取多少？不同检索源需要加权吗？

这道题问的是工程调参的细节。

**我的回答** ：默认 60，来自原论文的实验结果。但这不是铁律，得在自己数据集上跑评测调整。如果某一路检索器明显更强，可以加权：

![公式](https://mmbiz.qpic.cn/mmbiz_svg/Q3auHgzwzM7ZQbLlhxvShria7PSibAvM6cAoRhNmrqrTsEsFN0NztOCkPpWPGAq50YTTYRgfWlibrChaedZGtCS20DZyhicias98jjRWjick7FIxgJ8VRSN7ZY8A/640?wx_fmt=svg&from=appmsg#imgIndex=2)

但要小心，权重别调太大，不然某一路上升到前面，其他路就形同虚设了，丧失了多路融合的优势。

**面试官补充** ：我们在高德里，不同检索源确实权重不同，比如地名库的精确匹配权重就会高一些。这个需要 **线上 A/B 测试来定** 。

## 5\. 初排已经给出顺序，为什么还需要重排？

这个问题问的是检索系统的经典架构—— **为什么有两阶段排序** 。

**我的回答** ：初排（粗排）是快召回，用的模型简单，比如向量相似度或者 BM25，能从几百万文档里快速捞出几百个候选。但它的匹配是 **粗糙的** ，可能捞上来的文档只是关键词碰上了，语义上并不相关。

精排（重排）会用更复杂的模型，比如 Cross-Encoder，同时看问题和文档，做细粒度的语义匹配，把真正有用的排到前面去。

**举个例子** ：

用户搜“怎么用身份证坐高铁”：

- 粗排捞上来的可能是：“身份证办理流程”、“高铁购票指南”、“高铁站乘车须知”
- 精排会把“高铁乘车须知”里提到身份证验票的那段排到最前面

初排保召回，精排保准确，各司其职。

## 6\. 粗排和精排分别有什么作用？为什么不能全量精排？

这个问题其实是在问 **计算成本和质量之间的权衡** 。

**我的回答** ：粗排是 **高召回、低精度、快** ，负责从海量数据里筛一遍。精排是 **低召回（针对全量来说）、高精度、慢** ，负责对少量候选做精细判断。

不能全量精排的核心原因是 **太慢了** 。一个 Cross-Encoder 模型处理一条文档可能要几十到几百毫秒，如果对 100 万条文档全做精排，单次请求的延迟就是分钟级别，线上根本不可用。

流程上大概是：

```
全量索引 (百万/千万级)
    ↓ 粗排 (BM25/双塔向量，毫秒级)
Top-K 候选 (几百级)
    ↓ 精排 (Cross-Encoder，几十毫秒/条)
Top-N 结果 (几十级)
    ↓ 最终输出
```

**面试官追问** ：粗排和精排的模型选型有什么讲究？

我说粗排一般用双塔结构（可以离线建索引），精排用 Cross-Encoder（效果好但计算重）。他说对，还补充了一句： **粗排不追求 perfect，只追求不漏掉 relevant** 。

## 7\. Markdown、PDF 怎么切分才能保留文档层级？

这道题是问 **文档预处理** 的，很实操。

**我的回答** ：

Markdown 好办，按 `#` 、 `##` 、 `###` 识别标题层级，段落和代码块用空行或反引号分隔。切分的时候在元数据里存上完整的标题路径，比如 `["第三章", "2.1节", "代码示例"]` ，这样检索的时候能知道这段内容在文档里什么位置。

PDF 就复杂了。它本质上是一堆坐标和字符，得用版面分析（layout analysis）识别出标题、正文、表格、图片。还要处理跨页段落——有些段落从第 3 页末尾开始，在第 4 页继续，得拼起来再切。

**关键原则** ： **不要只按固定字符数生切。** 那样会把完整的语义单元切断，检索效果会很差。

我补充了一句：切分的时候最好保留 **父子关系** 和 **相邻块信息** ，这样即使某一段本身没命中，也能通过父标题或相邻段落补充上下文。

## 8\. Agent 处理文档时超出上下文窗口怎么办？

这个问题问的是 LLM 上下文不够用的时候怎么处理长文档。

**我的回答** ：

方案有几个：

1. **递归切分** ：把长文档按章节或段落拆成小块，每块单独处理
2. **Map-Reduce 式总结** ：每个小块先做局部摘要，再把摘要汇总成整体摘要
3. **树状总结** ：小块合并成中块，中块再合并成大块，逐层汇总
4. **按需检索** ：不一次性加载全文，只把当前任务真正需要的内容检索出来塞进上下文

**面试官追问** ：什么时候用摘要，什么时候用检索？

我说：摘要适合“整体理解”类任务，比如“这本书讲了什么”；检索适合“具体查找”类任务，比如“这本书里怎么定义强化学习”。他点头。

## 9\. Skill 和 MCP 扩展 Agent 能力的本质区别是什么？

这个问题涉及目前 Agent 领域两个很火的概念，我特意准备过。

**我的回答** ：

**Skill** 是面向具体任务的“能力包”，里面可能包含提示词、工具调用流程、代码片段、输出规范等。比如“发送邮件”这个 Skill，会定义怎么调用邮件 API、怎么写邮件内容、怎么处理发送失败的情况。

**MCP** （Model Context Protocol）是一种 **标准化接入协议** ，用来让 Agent 发现和调用外部工具、资源和服务。它解决的是“怎么让 Agent 和各种工具对话”的问题。

打个比方： **Skill 是菜谱，告诉你红烧肉怎么做；MCP 是厨房里统一的插座标准，让你能把不同牌子电器都接上电。**

具体到架构上：

```
Agent
  ├── Skill 层：具体任务逻辑
  │   ├── 代码检索 Skill
  │   ├── 文档总结 Skill
  │   └── 地图导航 Skill
  └── MCP 层：统一接入
        ├── 数据库工具
        ├── 搜索 API
        ├── 内部业务系统
        └── 第三方服务
```

Skill 描述“如何做”，MCP 解决“如何标准化接入”。

## 10\. Agent 如何记住历史对话？Memory 模块如何运行？

这道题答得一般，面试后我又查资料补充了一下。

**我的回答（面试时）** ：

短期记忆就是当前会话里的消息列表、任务状态、工具调用结果。长期记忆会把用户的稳定偏好、历史事实存到数据库或向量库里。

新问题来了之后，系统会从长期记忆里检索相关记忆，注入到上下文里。同时还要处理记忆的 **更新、冲突、过期和隐私** 问题。

**面试官追问** ：记忆冲突怎么处理？

我说：按时间戳覆盖，或者让 LLM 判断哪个更可信。他说可以再想想，如果两个事实时间相近但矛盾，可能需要引入置信度评分。

**补充一下标准架构** ：

```
用户输入
    ↓
短期记忆（当前会话）
    ├── 对话消息
    ├── 任务状态
    └── 工具执行结果
    ↓
长期记忆检索（向量相似度）
    ↓
记忆融合 + 冲突消解
    ↓
注入上下文 → LLM 生成
    ↓
更新短期/长期记忆
```

## 11\. 对话轮次增加导致上下文膨胀，有哪些解决方案？

这道题问的是 **上下文窗口管理** ，很实用。

**我的回答** ：

常见方案：

- **滑动窗口** ：只保留最近 N 轮对话
- **历史摘要** ：用 LLM 把旧对话压缩成摘要
- **按需检索** ：不保留全部历史，按需要从记忆库检索
- **工具结果精简** ：删除重复的、低价值的工具返回内容

工程上要设定 **Token 预算** ，优先保留：系统指令 > 当前任务关键信息 > 最近对话 > 历史摘要。

不要机械地保留全部消息，那是资源浪费，而且会稀释重要信息。

## 12\. ReAct 推理与行动交替的完整流程是什么？

这道题考的是 Agent 的核心执行模式。

**我的回答** ：

ReAct = Reasoning + Acting，核心就是 **想一步、做一步、看一步** ：

1. **推理** ：模型看当前状态，决定下一步做什么（比如“需要查一下今天的天气”）
2. **行动** ：调用工具执行（比如调用天气 API）
3. **观察** ：拿到工具返回结果（“晴天 28°C”）
4. **循环** ：基于观察结果继续推理，直到信息足够
5. **生成最终答案**

流程上长这样：

```
用户问题："北京明天适合郊游吗？"
    ↓
[推理] 需要知道天气和空气质量
    ↓
[行动] 调用天气 API
    ↓
[观察] 晴天 28°C，AQI 75
    ↓
[推理] 天气不错，可以推荐郊游
    ↓
[生成] "明天北京天气晴朗，空气质量良好，适合郊游。推荐去香山。"
```

**工程上还要考虑** ：最大步数限制、单步超时、权限校验、工具调用失败时的兜底策略（比如返回“暂时无法获取信息”）。

## 13\. ReAct 和 Agent Loop 都是循环，本质区别在哪里？

这个问题是我面得最懵的。说实话当时想了一会儿。

**我的回答** ：

ReAct 是一种 **具体的 Agent 策略** ，强调“推理→行动→观察”这种交替模式。

Agent Loop 是 **更通用的运行框架** ，负责管理：模型调用、工具执行、状态更新、终止条件。

Agent Loop 可以运行 ReAct 策略，也可以运行其他策略，比如：

- **Plan-and-Execute** ：先做完整计划，再批量执行
- **Reflection** ：执行完反思结果，再决定要不要重试
- **Parallel Execution** ：同时执行多个独立的工具调用
- **Human-in-the-Loop** ：某些步骤需要人工确认

**用一个图表示** ：

```
Agent Loop（框架层）
  ├── 循环控制：终止条件、最大步数、超时
  ├── 状态管理：当前上下文、已执行步骤、中间结果
  └── 策略插件（可插拔）
        ├── ReAct（推理→行动→观察）
        ├── Plan-and-Execute（计划→执行→汇总）
        ├── Reflection（执行→反思→重试）
        └── 其他自定义策略
```

所以 ReAct 是 Agent Loop 的一种“运行模式”，Agent Loop 是装着这个模式的“引擎”。
