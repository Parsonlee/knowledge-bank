# Python 并发与并行机制

## 全局解释器锁 (GIL) 的物理约束
在 CPython 默认实现中，**全局解释器锁（Global Interpreter Lock，简称 GIL）** 是一个互斥锁，用于保护 Python 对象免受多线程并发修改的影响，从而防止内存管理中的竞争条件。
- **并行约束**：由于 GIL 的存在，**同一时刻只允许一个线程执行 Python 字节码**。
- **性能阻碍**：这意味着即便是在多核 CPU 的机器上，运行纯 CPU 密集型（CPU-bound）任务时，使用多线程也无法利用多核硬件来实现物理上的并行计算，甚至会因为线程频繁切换而导致额外的性能损耗。

## 四种并发与并行技术对比

Python 开发者目前可以通过以下四种主要技术来处理并发与并行任务：

| 技术维度 | 多线程 (Threads) | 多进程 (Multiprocessing) | 协程 (Coroutines / Async) | 子解释器 (Subinterpreters) |
| :--- | :--- | :--- | :--- | :--- |
| **GIL 限制** | 共享单个 GIL | 每个进程拥有独立的 GIL | 共享单个 GIL | 每个子解释器拥有独立的 GIL |
| **内存空间** | 共享进程内存空间 | 彼此完全隔离 | 共享单个线程内的内存空间 | 彼此隔离，默认不共享全局对象 |
| **执行模型** | 抢占式多任务（由 OS 调度） | 物理多核并行进程 | 协作式并发（显式 `await` 切换） | 单进程内的多核物理并行 |
| **开销与速度** | 极轻量，启动快 | 较重，进程启动开销大 | 极轻量，单线程内上下文切换快 | 介于线程与多进程之间，比进程轻量 |
| **通信机制** | 直接读写共享内存（需加锁） | 进程间通信（IPC，如 Pipes, Queues） | 直接共享（无锁竞争，因单线程） | 消息通道（Channels），避免并发冲突 |
| **成熟度/版本** | 历史悠久，非常成熟 | 历史悠久，非常成熟 | Python 3.5+ 引入 `async/await`，成熟 | Python 3.12+ 引入，仍在实验阶段（3.14+ 完整） |

### 1. 多线程 (Threads)
多线程是在同一个进程下启动多个轻量级工人。因为它们共享同一块内存，数据共享极快。但是由于 GIL 的硬性限制，在执行 CPU 密集型计算时，线程之间只能交替轮流运行，无任何加速效果。不过，**在遇到 I/O 阻塞（如读写磁盘、网络请求）时，CPython 会主动释放 GIL**，因此多线程非常适用于 I/O 密集型任务。

### 2. 多进程 (Multiprocessing)
多进程通过开启完全独立的 Python 操作系统进程来绕过 GIL 限制。每个进程都有自己独立的 Python 解释器和独立的 GIL，从而能够在多核 CPU 上实现真正的物理并行。
- **局限性**：进程启动的资源与时间开销较大（不适合微小的短耗时任务）；进程之间内存完全隔离，如果需要数据交换，必须通过序列化/反序列化进行进程间通信（IPC），极易遇到通信性能瓶颈。

### 3. 协程 (Coroutines)
协程是在单个线程内运行的协作式多任务。它不需要操作系统的内核级线程切换，而是由程序（如 Python `asyncio` 事件循环）在遇到 `await` 异步调用点时，显式且主动地交出控制权给其他任务。
- **关键差异**：**协程只提供“并发”（同时处理多个任务的能力），而不提供“并行”（同时物理执行多个任务的能力）**。对于纯 CPU 计算任务，由于没有 `await` 交出控制权，协程会退化为纯单线程顺序执行，没有任何加速收益。它专门用于高并发的网络 I/O 场景。详细机制差异可参见 [[concepts/概念_Python_async_await并发]]。

### 4. 子解释器 (Subinterpreters)
Python 3.12 引入了子解释器（通过 `InterpreterPoolExecutor` 等 API），旨在提供一种介于多进程与多线程之间的折中方案。
- **机制**：在同一个进程中创建多个彼此隔离的子解释器，每个解释器拥有独立的 GIL 和内存空间。这使得它们能够安全地并行运行在多核 CPU上，同时避免了多进程那样庞大的操作系统进程创建开销。
- **现状**：目前仍处于实验阶段，早期版本（Python 3.12 和 3.13）中未能获得完全的性能释放，预计需到 Python 3.14 之后该技术才趋于成熟和推荐用于生产环境。

## 自由线程（Free-threaded Python）与无 GIL 的演进
Python 3.13 引入了 **自由线程构建（Free-threaded Python）** 实验性特性，允许用户在编译或运行时完全禁用 GIL。
- **演进优势**：一旦禁用 GIL，多线程可以直接像 C++ 或 Java 线程一样，自动调度到多核 CPU 上执行物理并行计算，无需再依赖多进程或子解释器来获取并行能力。
- **当前局限与开销**：
  1. **单线程性能下降**：由于缺少了 GIL 带来的简单同步，无 GIL 构建为了维护线程安全，会在单线程执行中引入额外的锁开销，导致单线程代码性能下降 **10% 到 40%**。
  2. **生态兼容性**：大量的第三方 C 扩展库（如 numpy, pandas 等历史包）的代码深度依赖 GIL 存在的假设。移除 GIL 可能会引发隐蔽的段错误（Segmentation fault）或数据损坏。
  3. **过渡阶段**：预计社区需要 2 - 3 年的时间去优化生态兼容性并减少单线程开销，未来自由线程将逐步成为默认选项。

## 并发与并行决策矩阵

在自由线程成为默认选项之前，可参考以下决策树来选择并发方案：

```
                           任务类型是什么？
                              /        \
                    [ CPU密集型 ]    [ I/O密集型 ]
                       /                  \
             需要真物理并行吗？         并发量级有多大？
                /       \                /       \
             [是]       [否]         [高并发]   [中/低并发]
             /             \           /             \
       优先选择:         不用优化  优先选择:       优先选择:
    [Multiprocessing]            [Coroutines]     [Threads]
    (实验性可选:                  (async/await)   (多线程共享内存)
    Subinterpreters)
```

- **使用多线程（Threads）**：任务属于 I/O 密集型（如数据库查询、file读写），且线程数较少，且需要频繁共享进程内内存。
- **使用多进程（Multiprocessing）**：任务属于 CPU 密集型（如大规模图像处理、矩阵运算、机器学习推理），且可以接受进程启动和 IPC 开销。
- **使用协程（Coroutines）**：需要处理成千上万个高并发的网络 I/O 链接（如异步爬虫、高性能 Web API 服务器）。
- **使用子解释器（Subinterpreters）**：在 CPU 密集型任务中需要多核并行，但多进程的内存和系统开销过大，且能接受实验性特性的潜在风险。
