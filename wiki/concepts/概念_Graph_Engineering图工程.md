# 概念定义
**图工程（Graph Engineering）** 是多智能体（Multi-Agent）系统中的协调与编排层。当系统中的多个自主循环（Loops）需要协同工作时，就会产生复杂的协调问题，图工程就是利用图（Graph）的拓扑结构来描述、控制和约束这些协调关系的工程实践。

图工程包含三大物理要素：
1. **Nodes（节点）**：具体的工作单元。可以是单个大语言模型（LLM）调用、确定性代码函数、外部工具调用，或者是人类的介入审批。
2. **Edges（边）**：决定节点之间的执行流向。支持顺序执行（Sequence）、并发分叉（Parallel）或根据上一个节点输出进行条件分流（Conditional Routing）。
3. **State（共享状态流）**：在节点之间流转的共享数据对象。每个节点在执行时都会读取 State，并在执行完毕后将结果写回 State。

# 系统同轴架构嵌套关系
在 AI 应用系统的演进中，系统架构呈现为一个多层嵌套的同轴系统，每一层都包裹着前一层：

```
+-------------------------------------------------------------+
| Graph Engineering (图协调层: 跨 loops 路由与编排)             |
|   +-------------------------------------------------------+ |
|   | Loop Engineering (自主智能体循环: 目标导向自主循环)     | |
|   |   +-------------------------------------------------+ | |
|   |   | Harness Engineering (运行沙箱与副作用管理)      | | |
|   |   |   +-------------------------------------------+ | | |
|   |   |   | Context Engineering (上下文装配与检索)     | | | |
|   |   |   |   +-------------------------------------+ | | | |
|   |   |   |   | Prompt Engineering (提示词设计)     | | | | |
|   |   |   |   |   +-------------------------------+ | | | | |
|   |   |   |   |   | Model (底座大语言模型)         | | | | | |
|   |   |   |   |   +-------------------------------+ | | | | |
|   |   |   |   +-------------------------------------+ | | | |
|   |   |   +-------------------------------------------+ | | |
|   |   +-------------------------------------------------+ | |
|   +-------------------------------------------------------+ |
+-------------------------------------------------------------+
```

每一层的设计都必须稳固：**如果底层的工程设计（如 Harness 或 Context）存在缺陷，上层的 Graph 就会以更复杂、更难调试的方式发生级联失败。**

# 图工程四大痛点设计准则

为了防止图工程设计过度复杂或系统迅速腐烂，实践中需要遵循以下四大黄金准则：

### 1. 节点存在合理性（Node Justification Specialty 审查）
- **痛点**：容易过度设计，将一个简单的任务（如“总结 PDF”）拆分为臃肿的多节点图（下载器-分块器-总结器-评审器-格式化器）。
- **准则**：节点只有在代表**真正的专业分工**（例如需要不同的模型家族、不同的工具集，或扮演完全独立的只读评审角色）时，才被允许物理存在。任何可以在一个 Loop 中内联（Inline）完成的步骤都不应独立成节点。如果无法在餐巾纸上清晰画出这个图，或者合并两个节点没有带来任何损失，则说明设计过载。

### 2. 共享状态防漂移与防腐（State Management）
- **痛点**：所有节点共享同一个 State 对象，若发生无约束的乱写，脏数据会在后续节点间级联扩散，直到最终输出错误，且难以定位污染源。
- **准则**：
  - **Typed Schema**：为 State 定义强类型的 Schema（如使用 Pydantic 定义字段类型）。
  - **Write Permission**：明确规定哪些节点对哪些字段拥有写权限。
  - **State Checkpoint & Replay**：在节点间对 State 进行 Checkpoint 归档，方便随时重放（Replay）调试。
  - **幂等副作用管理**：重放时后续节点会二次执行，因此任何具有外部副作用（如发邮件、数据库写入）的节点必须实现幂等。

### 3. 确定性路由（Deterministic Routing）
- **痛点**：由大模型在 Edge 上动态决定下一步去向，会导致极大的不确定性与路由漂移，让调试和回归测试变得异常痛苦。
- **准则**：**确定性代码（Deterministic Edge Code）优先**。只要路由条件是可程序化校验的，就应该使用传统代码进行路由控制；只有在涉及需要真正人类语义理解和主观判断的步骤时，才分配给模型决定。

### 4. 对抗验证（Reviewer Optimization）与 Single Writer 机制
- **痛点**：同质化智能体容易“相互包庇”。若 20 个节点基于相同的基座模型、共享同一个上下文，它们很容易对错误的生成结果达成一致（模型倾向于偏爱自己或同族模型的输出）。
- **准则**：
  - **对抗验证**：评审节点（Reviewer）必须使用**不同的模型家族**，并传入**干净的上下文（Clean Context，不带前面的冗长对话历史）**。此外，评审结果应锚定于**外部运行的物理实体测试证据**（如测试是否通过、代码是否成功编译等），而不是单纯让模型主观评价。
  - **Single Writer 机制**：采用 Cognition（Devin 开发商）的实践，允许并行阅读/讨论，但整个图中**只有单一 Agent 拥有物理写权限（Single Writer）**，以此避免并发冲突和状态污染。
