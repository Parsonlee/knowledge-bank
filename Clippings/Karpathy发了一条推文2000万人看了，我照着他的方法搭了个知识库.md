## Karpathy发了一条推文2000万人看了，我照着他的方法搭了个知识库

> wuhiufan

4月2日，Andrej Karpathy在X上发了一条推文，讲他怎么用LLM搭个人知识库。

这条推文获得了超过1500万次浏览、9万次收藏。之后他又发了一份详细的GitHub Gist，把完整架构设计、操作流程、工具推荐全写了出来。

全网讨论度超过2000万阅读。

我花了两天时间照着他的方案搭了一个，现在跑了一个多月。说实话，体验跟我之前用的所有"AI知识库"都不一样——不是搜索，是编译。

---

## 先说清楚：这跟RAG有什么不同

现在市面上大多数"AI知识库"都是基于RAG（检索增强生成）的。你问一个问题，它在知识库里搜相关片段，拼在一起喂给大模型，生成回答。

Karpathy觉得RAG有四个结构性问题：

**问题一：分块切割导致语义断裂。** 小片段检索精度高但丢失上下文，大片段保留上下文但匹配模糊。研究数据显示语义分块平均只有43个token，上下文太少导致答案不准。

**问题二：每次查询都是无状态的。** 查询结果用完就丢，没有积累。你问过的问题、得到过的答案，下次还得重新搜一遍。

**问题三：规模越大越不准。** 知识库一大，"大海捞针"成功率显著下降，而且存在"中间内容被忽略"现象。

**问题四：嵌入模型会过时。** 换一次嵌入模型就得重新嵌入整个语料库，持续的计算开销。

Karpathy的思路完全不同： **不是每次查询都重新检索，而是让LLM提前把知识"编译"成一套结构化的Wiki。**

用编译器做类比：

| 编译器概念 | LLM Wiki对应 |
| --- | --- |
| 源代码 | 原始文档（文章、论文、笔记） |
| 编译产物 | Wiki页面（结构化Markdown） |
| 编译器 | LLM |
| 构建配置 | Schema（规则文件） |
| 增量编译 | 新文档进来，只更新受影响的页面 |
| 依赖图 | 交叉引用和反向链接 |
| 代码检查 | Wiki健康检查 |

RAG相当于每次运行程序都重新编译整个项目。LLM Wiki把知识编译成了可直接使用的产物，查询时读产物就行。

## 三层架构

整个方案分三层：

**第一层：Raw（原始素材）**

你收集的文章、论文、笔记、数据。这层不可变，LLM只读不写。是真相的锚点。

**第二层：Wiki（编译产物）**

LLM生成和维护的Markdown文件。包含摘要页面、实体页面、概念页面、对比分析、主题导航。这层LLM完全拥有——你读它，LLM写它。

**第三层：Schema（规则配置）**

告诉LLM怎么组织Wiki的规则文件。Claude Code用 `CLAUDE.md` ，Codex用 `AGENTS.md` 。这个文件决定了LLM是有章法的Wiki维护者还是漫无目的的聊天机器人。

目录结构长这样：

```
wiki-root/
├── CLAUDE.md              # Schema：定义wiki结构和工作流
├── raw/                   # 第一层：不可变的原始资料
│   ├── articles/          # 网页文章
│   ├── papers/            # 学术论文
│   └── transcripts/       # 播客/视频文字稿
├── wiki/                  # 第二层：LLM维护的Wiki
│   ├── index.md           # 总索引
│   ├── log.md             # 操作日志
│   ├── entities/          # 实体页面（人物、公司、工具）
│   ├── concepts/          # 概念页面（理论、框架）
│   ├── sources/           # 来源摘要
│   └── comparisons/       # 对比分析
└── assets/                # 图片、图表
```

## 四个核心操作

### 操作一：摄入（Ingest）

往 `raw/` 目录放新文档，告诉LLM处理它。完整流程：

1. LLM阅读完整的原始文档
2. 跟你讨论关键要点（2-3条摘要）
3. 等你确认后，在 `wiki/sources/` 创建来源摘要
4. 更新或创建相关的实体页面
5. 更新或创建相关的概念页面
6. 检查新来源和已有Wiki内容之间的矛盾
7. 更新所有受影响页面的交叉引用
8. 更新索引和日志
9. 向你报告：创建了什么、更新了什么、有没有矛盾

一个信息来源可能触发10-15个Wiki页面的更新。

实际操作时，你跟Claude Code说"ingest raw/articles/xxx.md"，它就自动跑完上面9步。

### 操作二：查询（Query）

对Wiki问问题，LLM搜索相关页面，阅读它们，综合出带引用的回答。

关键设计： **好的回答可以回填到Wiki作为新页面。** 探索和查询也在Wiki中"积累"，不会浪费。

### 操作三：索引（Index）

`index.md` 是内容导向的总目录，每个页面一行摘要。LLM回答查询时先读索引找到相关页面，再深入细节。

`log.md` 是按时间顺序的操作记录，纯追加。可以用grep快速查询历史操作。

### 操作四：健康检查（Lint）

定期让LLM给Wiki做体检，检查项包括：  
\- 页面之间的矛盾  
\- 过时的内容  
\- 孤立页面（没有任何入链）  
\- 占位符页面（创建了但内容太少）  
\- 缺失页面（被引用但不存在的）  
\- `raw/` 里还没摄入的文件

## 我搭好之后的实际体验

跑了一个多月，我的Raw层积累了大概80篇素材，Wiki层有130多个页面。

**最大的感受是"知识在生长"。**

以前用RAG知识库，每次问问题感觉都是"从零开始搜"。现在问问题，LLM直接读已经编译好的Wiki页面，回答里带交叉引用、带来源标注、带矛盾提示。质量明显高一截。

而且摄入新文章的时候，LLM会自动检查跟已有内容的矛盾——有一次我摄入了一篇新文章，它主动标注"这篇文章的结论跟你之前摄入的第23号来源矛盾，建议确认"。

这种"持续编译、持续积累"的感觉，是RAG给不了的。

## 工具链

**Claude Code或Codex** ：负责执行摄入、查询、健康检查这些操作。推荐Claude Code，它的Edit工具用精确字符串匹配做替换，可以在500行的Wiki页面里只改一段话，比全文重写安全。

**Obsidian** ：浏览和阅读Wiki。Karpathy原话："Obsidian是IDE，LLM是程序员，Wiki是代码库。" 自带的Graph View能直观查看Wiki结构，孤立节点一目了然。Dataview插件可以对frontmatter做动态查询。

**==qmd==** ==：当Wiki增长到300+页面时，index.md本身就要消耗15K+ tokens，这时候需要搜索引擎。qmd是本地Markdown搜索引擎，支持全文检索、语义搜索和混合搜索三种模式。==

**Git** ：整个Wiki就是Git仓库里的Markdown文件。 `git diff` 看LLM改了什么， `git log` 看页面演变历史，出问题就回退。

## 从Memex到LLM Wiki：八十年的思想谱系

这套思路其实不是Karpathy凭空想出来的，有一条80年的思想脉络。

**1945年，Vannevar Bush提出Memex。** 他在《大西洋月刊》发文设想一种设备，能存储所有书籍和记录，核心创新是"关联性路径"——用户可以把两个项目永久连接起来，形成可翻阅的路径。万维网实现了超链接，但Web的链接是单向的、没人维护的。Memex的核心特征——私有的、主动策划的、连接和文档本身一样有价值——恰好是LLM Wiki的特征。

Bush没能解决的问题是：谁来做维护？

**1950年代到1998年，Niklas Luhmann用人力做到了。** 这位德国社会学家用卡片盒系统管理知识，到去世时积累了9万张索引卡，每张只包含一个原子化想法，通过编号和标签互相链接。用这套系统产出了70本书和400多篇学术论文。

Luhmann的核心理念：卡片盒是"对话伙伴"，你向它提问，它通过关联给出你没预料的答案。

**2026年，Karpathy用LLM自动化了维护。** Bush构想愿景，Luhmann用人力纪律实现，Karpathy用LLM接手了最烦人的维护工作。

---

## 为什么这套方案能成立

维护知识库最烦人的部分永远是记账——更新交叉引用、保持摘要最新、在几十个页面间维持一致性。

人类放弃Wiki是因为维护成本的增长速度超过了使用价值的增长速度。

LLM不会觉得无聊，不会忘记更新交叉引用，可以一次修改15个文件。Wiki能持续运转下去，是因为维护成本接近于零。

人的工作是策划来源、引导分析、提出好问题、思考意义。LLM的工作是其余的一切。

## 你要上手的话

别被架构吓住。最小可用版本就三步：

1. 建一个文件夹，放一个 `CLAUDE.md` （写清楚你的Wiki结构规则）
2. 往 `raw/` 目录放几篇文章
3. 跟Claude Code说"ingest raw/articles/xxx.md"

跑通一次摄入，你就理解这套方案了。剩下的索引、健康检查、qmd搜索引擎，都是规模大了之后才需要的。

GitHub上已经有社区实现可以参考，搜索 `llm-wiki-compiler` 或 `awesome-llm-knowledge-bases` 就能找到。

Karpathy没有开源代码，他发了一份"idea file"。原话是："你只分享想法，对方的Agent会根据具体需求定制和构建。"

这篇文章也是这个意思——思路给你了，具体怎么搭，你的AI助手能帮你搞定。
