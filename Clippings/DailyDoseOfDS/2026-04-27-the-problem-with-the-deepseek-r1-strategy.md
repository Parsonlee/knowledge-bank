# DeepSeek R1 策略存在的问题（The problem with the DeepSeek R1 strategy）

***********
问题所在
***********

GRPO 本身是通用的。

它不关心奖励是来自数学验证器、代码编译器、人类还是 Python 脚本。

它只需要每个回答的一个分数值，并在每组内进行归一化以产生训练信号。

但这里明显的一个瓶颈是这些奖励是从哪里来的。

对于数学和代码来说，这不成问题，因为环境会提供确定性的信号。

但是与现实世界的工具和数据进行交互的代理（Agents），并不能产生你可以用来跟黄金标准答案进行字符串匹配的输出。

一个 RAG 代理检索上下文并生成回答。这里没有单一的正确答案可以用来比较。一个客户支持代理起草回复。没有编译器可以运行它。一个摘要代理浓缩了一份 20 页的文档。这里存在许多同样有效的摘要，没有任何字符串匹配验证器能够区分出一份优秀的摘要和一份平庸的摘要。

在这些情况下，环境不会像数学题那样直接递给你一个奖励信号。

当然，有些代理任务确实有可验证的结果，对于这些任务，RLVR 运行得非常好，甚至涉及多步工具使用也能胜任。可验证性取决于任务的结果，而不是模型是否充当代理。

但对于大多数代理工作流来说，结果是主观的或多维度的。

直觉上，GRPO 仍然是合适的选择，因为采取多步操作、调用工具并合成响应的代理，会从探索中学习、尝试不同方法，并因有效的方法而获得强化中获益。

因此，虽然 RL 框架是合适的，但缺失的部分是评分函数。

一种解决方案是编写自定义奖励函数，由 Python 代码根据手动定义的标准对每个输出进行评分。

* 一个 RAG 奖励函数可能会检查响应是否使用了检索到的上下文（忠实度），对不在上下文中的内容进行惩罚（幻觉），奖励完整性，并处理上下文本身模糊不清的情况。
* 一个工具使用的奖励函数可能会在多步任务中对部分进度进行评分，惩罚不必要的 API 调用，并衡量代理是否达到了正确的最终状态。

每个标准返回一个部分分数，然后将这些分数求和或加权得出一个最终奖励。

这种方法行得通，但它带来了自身的一系列问题。

编写一个好的奖励函数需要数天的迭代。研究人员需要预测边缘情况，校准不同标准之间的权重，并测试该函数是否真正奖励了你想要的行为。

一个过度重视格式遵从而对忠实度赋予权重不足的奖励函数，将会训练出一个生成排版精美却充满幻觉的代理。

奖励函数也很脆弱。如果你更改了检索管道、添加了新工具或修改了系统提示，奖励函数就需要被重写。

调试也是有问题的。

当代理在训练期间学到了不良行为时，原因可能是奖励函数、训练超参数、数据，或者完全是其他东西。

但由于奖励函数是自定义代码，直到你已经用它训练了一个模型并评估了输出之后，你通常无法分辨该函数是否正在测量你认为它正在测量的东西。

这就是强化学习被广泛应用于可验证任务（数学、代码、逻辑）而没有被应用于代理工作流（RAG、客户支持、工具使用、摘要）的主要原因。

RLVR 为推理模型提供了一种通用的、自动的奖励信号，它们可以在其中检查答案并返回 0 或 1。但对于大多数代理工作流，不存在这样的等价物。

这种区别与模型无关。同一个 Qwen 2.5 14B 可以胜任这两种角色。

这种区别与任务有关。我们能够验证一个代理是否正在产生可以被自动检查的输出吗？
