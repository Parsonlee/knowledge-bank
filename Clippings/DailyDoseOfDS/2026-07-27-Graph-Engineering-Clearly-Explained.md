通俗易懂地讲解 Graph Engineering（图工程）
当你拥有多个循环（Loop）需要相互配合时，你就会面临协调问题。而在工程学中，工程师们向来习惯于用**图（Graph）**来描述协调关系。这就是 Peter Steinberger 近期提及的“图工程（Graph Engineering）”的核心思想。
1. 什么是图（Graph）？
一个图包含三个核心要素：


* 节点（Nodes）：工作单元。可以是 Agent、普通的模型调用、确定性函数、工具调用或人工审批节点。
* 边（Edges）：决定下一步运行什么。可以是顺序执行、并行执行，或根据上一个节点的输出结果进行条件路由。
* 状态（State）：沿着边流动的共享对象。每个节点都会从中读取数据并向其中写入数据。
单 Loop 与 Graph 的关系
经典的示例图通常包含三个节点（研究员收集资料、作者撰写草稿、审稿人评审）。如果评审通过，流程结束；如果失败，则通过一条带有 Loop 的边退回给作者重新修改。 关键推论：单 Agent 循环本质上就是一个只有一个节点且一条边指向自身的“单节点图”。图并不是要取代 Loop，而是用来连接和管辖多个 Loop。

2. AI 技术栈的演进
AI 的重置重心正在逐渐从模型本身向外扩展：


* Prompt Engineering（提示工程）：你发送给模型的提示词。
* Context Engineering（上下文工程）：模型能看到的所有信息（不限于指令）。
* Harness Engineering（框架工程）：围绕模型运行工具、追踪状态和处理异常的外围代码。
* Loop Engineering（循环工程）：驱动单个 Agent 走向目标的自主循环。
* Graph Engineering（图工程）：跨多个 Loop 的协调层，涵盖何时运行、按何顺序运行以及谁来监督谁。


每一层都包裹着上一层：图由 Loop 组成，Loop 需要优秀的 Harness，Harness 调用属于 Context 问题，而每个 Context 都包含 Prompt。

3. 图工程的四大难题
难题 1：判断一个节点是否有资格独立存在
最常见的失败是将“总结 PDF”拆解为一个包含抓取器、切块器、总结器、审稿人和格式化器的五节点复杂图。 原则：只有当一个节点代表真正的专业职责/角色（如不同模型、不同工具集或只读的审稿人）时，它才值得独立成为 Node。可以在已有 Loop 内内联完成的步骤不属于独立 Node。如果不能在餐巾纸上画清楚，说明架构过于复杂；如果合并两个节点毫无损失，说明它们本就是一体。
难题 2：保持共享状态的干净
在 Loop 中常见的问题是上下文腐化（Context Rot）；而在 Graph 中，这个问题转移到了共享状态对象中。 解决方案：


1. 为 State 赋予明确的类型化 Schema。
2. 明确规定哪些节点允许写入哪些字段。
3. 在节点间对 State 进行 Checkpoint 存盘，便于回放调试。注意：回放时具有外部副作用的节点（如发邮件、建记录）必须支持幂等（可重复执行）。
难题 3：可信赖的路由（Routing）
若由大模型完全决定路由边，虽有灵活性但缺乏稳定性，极其难调试。 原则：可预测的确定性路由由代码直接控制，只有真正需要语义理解与裁决的步骤才调用大语言模型。
难题 4：避免多 Agent 互相赞同（Echo Chamber）
如果 20 个基于相同基座模型的 Agent 在读取同一个有瑕疵的 Context，它们会倾向于赞同彼此的输出。 解决方案：


* 审稿人（Reviewer）节点使用不同的模型，并为其提供全新的上下文而非完整对话历史。
* 将裁决依据锚定在不可捏造的外部事实（如测试是否真的跑通、代码是否真的能编译）。
* 读写分离：允许多个 Agent 并行读取与评估，但只保留一个特定的 Agent 拥有写入和修改权限。

4. 何时使用 Graph？
大模型调用的 Token 消耗呈倍数增加（单 Agent 约为 Chat 的 4 倍，多 Agent 系统则可达 15 倍以上）。 决策规则：只有当任务明确拆分为独立专业领域、需要并行 Fan-out/Join、每个步骤需要不同模型、或者需要故障隔离与可审计路由时，才引入 Graph；否则，保持在简单的 Loop 中即可。
