# 11种LLM评估方法（11 LLM evaluation methods.）

一个模型可以正确回答问题，但在BLEU指标上得分接近零。

每当模型用与参考答案不同的话语说出正确内容时，就会发生这种情况。BLEU比较的是n-gram重叠度，因此一个简洁的改写会被判定为完全错误。

正是这一种失败导致了LLM评估被拆分为几种方法。每种方法都对正确输出的样子编码了不同的假设，而不同的指标在不同的用例中也是有用的。

让我们了解以下11种必知的LLM评估指标。

1) BLEU
将输出和参考答案拆分为n-gram，并衡量输出有多少受到参考的支持，带有长度惩罚以防止过短的输出通过省略获胜。它适用于翻译和受限生成（即参考措辞接近唯一可接受措辞的情况）。应报告语料库级别的BLEU，而不是平均句子分数，并在有多种正确措辞时提供多个参考。

2) ROUGE
翻转了BLEU的方向并测量召回率，意味着输出覆盖了参考答案的多少内容。它是摘要和信息提取的默认指标，在这些任务中遗漏内容比多余内容危害更大。ROUGE-L使用最长公共子序列，比ROUGE-2更能容忍语序调整。仅有召回率会奖励冗长，因此它需要搭配一个精度端指标。

3) BERTScore
嵌入两段文本，将每个输出token与最相似的参考token进行匹配，并在这些相似度上报告精确度、召回率和F1得分。它能处理在BLEU和ROUGE中引起麻烦的改写情况。绝对值通常处于一个较窄的高分区间，因此分数只有在跨系统比较时才有意义，不能直接读作准确率。重新缩放基线会有所帮助，同时嵌入模型必须匹配其领域和语言。

4) G-Eval
将任务描述和标准交给一个裁判模型，生成思维链评估步骤，然后对照这些步骤打分，结果通过token概率加权。它适合没有参考答案的主观标准，如语气、指令遵循或领域正确性。以具体检查清单编写的标准比以形容词编写的标准打分要一致得多。建议在低温度下运行裁判模型，并在信任它之前根据一小部分人工标注的集合进行校准。

5) LLM-as-Judge
成对比较形式将两个或多个输出连同评分量表送给裁判，裁判从中挑选出更好的那个。在绝对分数在不同运行中产生漂移时，它是比较两个模型、两个提示词或两个检索配置的实用方法。确保随机安排哪个输出先出现，因为裁判可能会偏向某一位置。同时需要控制长度，因为无论质量如何，裁判通常都会更喜欢较长的答案。

6) 人工评估 (Human eval)
标注者在定义的维度上对输出进行评分，聚合后的结果成为校准每个自动指标的基准参考。它适用于两个地方：构建验证裁判模型的校准集，以及发布前的最终把关。你必须在开始标注之前定义好量表，并测量标注者之间的一致性。低一致性意味着量表存在歧义，而不是标注者有错。

7) LLM陪审团 (LLM juries)
针对同一输出独立运行多个裁判，并将他们的分数平均为一个最终裁决。它的存在是因为单一裁判带有一种稳定的偏见，包括偏好自己所属模型家族的输出。使用不同的模型家族而不是将同一个模型使用三次，因为相关的裁判只能平均掉噪声而不能消除偏见。在较低成本下，陪审团中由几个小模型组成的效果通常击败单个大模型。

8) DAG
通过决策树打分，每个节点询问一个狭窄的问题，答案指向下一个节点，最终的叶子节点带有分数。它适合带有硬性要求和顺序的评分标准，比如格式合规性、必填部分或强制性免责声明。因为分支是确定性的，同样的输出总是得到相同的分数。应始终将低成本的确定性检查放在靠近根节点的位置，这样不合格的输出可以在调用任何模型之前退出。

9) 轨迹准确性 (Trajectory accuracy)
捕获代理完整的思考序列、工具调用和观察结果，然后将该路径与预期路径进行对照打分。这很重要，因为代理可能通过错误的路径得出正确的答案，将token浪费在冗余的调用或碰了不该碰的工具上。请分开为路径和结果打分，否则一个侥幸蒙对的答案就会掩盖损坏的执行路径。这需要首先就位追踪（tracing），因为如果没有追踪就没有轨迹可评分。

10) 多轮评估 (Multi-turn eval)
将整个对话作为整体单位，对角色遵循、跨轮次的知识保持和连贯性进行评分。单轮评分会遗漏随时间推移才显现的故障，比如自相矛盾地否定了之前的答案，或丢弃了五轮前设定的约束。在真实的对话日志上运行它，而不是在合成的两轮对话中运行，因为规则保持失败通常在深层才显现出来。

11) 安全性评估 (Safety eval)
在输出上并行运行偏见、有害性和PII分类器，并标记违规情况，而不是产生一个质量分数。它属于一道关卡，而不是平均数中的一项。无论平均质量分数看起来多好，只要有一次PII泄露就事关重大，这也是为什么将安全性折叠进总评分中最终会导致带有违规内容的发布。
