# Agent 需要一种全新的网络搜索方式（Agents need a new kind of web search）

Andrej Karpathy 曾经说过，大语言模型（LLM）有点像一个患有**顺行性遗忘症（Anterograde Amnesia）**的同事——这种病症的表现是你能保留旧记忆，但无法形成新记忆。

LLM 在两个层面上生活在这种状态下：它不会在不同对话之间记住你，也永远无法学习训练结束之后发生的任何事情。

记忆功能的存在是为了弥补第一个缺陷。而本文探讨的是第二个缺陷，因为 Agent 被雇佣主要是为了处理**当下**的事务。

市场在变动、人员在跳槽、价格在更新、新闻在爆发。网络搜索是模型感知这一切的唯一途径，而搜索的有效程度最终决定了整个 Agent 的实用价值。

因此，你为 Agent 挂载了一个搜索工具，假设它现在能够阅读网页了。但当你查看前几次的运行轨迹（Traces）时，结果令人失望：

你支付的绝大部分 Token 都花在了 Agent 必须精细梳理的原始网页文本上，只有极小一部分真正用于回答你的问题。

问题的根源在于搜索调用实际返回的内容。标准的搜索 API 仅仅手递手地给你返回几个链接和 30 个单词的摘要片段，仅此而已。

因此，Agent 并不是在阅读网页，它是在阅读一份**目录**。抓取真实网页成了它的工作——这意味着在开展任何实质性工作之前，它必须先拉取 HTML、剥离标记语言，并挖出可用的文本。

在单次查询中，你几乎感觉不到这种开销。但在需要多次搜索的任务中（如研究分析或简报生成流水线），你在每一次搜索时都在重复支付这笔费用。

问题的核心不在于 Agent 搜索得不够好，而在于**每次搜索调用返回的是内容的“指针”而非内容本身**，导致 Agent 在每次调用中都要花钱去填补这一鸿沟。

我们通过三种不同的检索架构运行了同一个问题，并统计了 Token 消耗。最昂贵的配置开销大约是最便宜选项的 **4 倍**。

本文将梳理这些数据，展示当读取者是 Agent 时搜索响应应该长什么样，同时涵盖一类**只有完整文档才能解答**的问题。

---

### 一、 成本究竟来自哪里？

**每一次循环迭代都要支付检索成本。**

这种重复的“抓取与清洗”工作有一个名字：**检索税（Retrieval Tax）**——即 Agent 在能够对你的问题进行推理之前，为了准备内容而烧掉的 Token。

仅仅一个循环运行的 Agent 就足以让你感受到这种压力。一个研究型 Agent 执行搜索、阅读返回内容、决定下一步查找什么，然后再进行搜索——每一次循环都在上一轮的基础上叠加支付检索税。

以下是解答单个问题所花费的成本。我们特意挑选了“什么是 Y2K？”这个问题，因为模型在预训练阶段就已经知道答案。

我们通过三种方式回答该问题：直接从模型记忆生成、通过网络搜索循环（Web Search Loop）、以及通过自建索引（Owned Index，一种预先抓取并清洗网页、存储自己处理过的数据副本的搜索服务），并统计每次计费的总 Token 数。

选择模型已知的问题能确保实验的干净可控：三种运行方式中的推理思考成本完全相同，因此多出来的 Token 完全来自于**检索本身**。

* **直接从记忆生成**：整个过程大约消耗 600 个 Token。这是基线，即零检索纯回答的成本。
* **自建索引（Owned Index）**：这种搜索服务已经预先抓取并清洗了网页，因此一次调用即可返回完整文档。走这种方式大约消耗 6,900 个 Token。
* **单次网络搜索循环**：单次网络搜索跳转消耗约 3,750 个 Token。但由于摘要片段往往太薄弱无法直接回答，Agent 会重新抓取并提炼，三次跳转后 Token 飙升至约 28,700 个——是自建索引的 **4 倍以上**。

循环搜索与自建索引之间的差距，就是肉眼可见的“检索税”。每一次跳转都会对不断增长的上下文窗口重新计费，因此到了第三次跳转时，Agent 主要是为了携带它之前已经阅读过的页面而付费。

自建索引跳过了这一切。当查询到达时，完整的文档已经准备好了。

### 二、 优秀的检索返回的是文档，而非方向

解决方案不是换一个更聪明的 Agent 或写更优秀的 Prompt，而是**改变搜索调用返回的内容**。

* **SERP（搜索引擎结果页）**：搜索 API 返回的纯结果列表，它给你 URL 并要求 Agent 自己去爬取网页。
* **Scraper-first 工具**：让你更进一步，返回原始 HTML 或 Markdown，但 Agent 仍需清洗才能使用。
* **Owned Index（自建索引）**：在查询到达之前就已经完成了所有这些工作，因此返回的内容已经是结构化的完整文档。

在所有三种模式中进行同一次查找：我们搜索《Interpretable Machine Learning》一书的作者 Christoph Molnar。

1) **SERP**：Agent 得到的是一串标签页列表，而不是答案。
2) **Neural search（神经网络搜索）**：它找到了正确的人，但只是高亮片段。获取完整记录仍需要另一次调用。
3) **Owned Index（自建索引）**：一次调用即可返回完整记录，Agent 直接进入推理阶段。

### 三、 有些答案仅存在于跨记录交叉分析中

完整文档解锁的能力远不止降低检索税。

**有些问题并不存在于任何单个搜索结果中。答案只有在你阅读多条记录并找到它们的交集时才会浮现。**

考虑一个 Market Go-To-Market（GTM）团队实际运行的问题：你需要找出在上个季度聘请了数据或 AI 领导角色的所有目标客户账号。

你可以查询人员作用域以找出最近跳槽到相关职位的人，然后与新闻作用域交叉比对触发事件。

最终输出的是一个经过排序的意向客户列表，并带有充分的上下文，足以针对每一个客户写出高相关度的首条触达话术。

---

### 四、 将探索与深度链式结合，让每次迭代更便宜

Seltz 并不是开放网络搜索的替代品，而是针对特定类型问题的合适工具。

一旦你明确了要找的内容，Seltz 会在一次跳转中返回完整记录，而不是返回一条标题加一个链接。

将两者链式结合：让每一次循环迭代都获得其真正试图完成的操作所对应的最佳检索形态。

这就是核心论点：Agent 循环的成本主要是由**每次搜索调用交回的内容**决定的，而返回成品文档就是你停止为同一个页面重复付费的方式。
